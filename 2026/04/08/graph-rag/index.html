GraphRAG
从检索到关联

让零散的文档，成为彼此连接的知识。

一句话理解

GraphRAG = 向量检索 + 知识图谱 + 社区摘要。

它不是只找“最像的几段文本”，而是先把文档里的实体、关系、主题社区组织起来，再回答需要跨文档推理、全局归纳、长链路关联的问题。

什么是 GraphRAG

GraphRAG 是微软提出的一种基于知识图谱的检索增强生成方法，相比传统 RAG，它更擅长处理需要跨文档推理和全局理解的问题。

传统 RAG 的局限

  • 基于向量相似度检索，难以捕捉文档之间的关系
  • 更容易回答“哪段最相关”，不擅长回答“整体说明了什么”
  • 当线索分散在多个文档中时，答案容易碎片化

GraphRAG 的改进

  • 先从文档中抽取实体和关系，构建知识图谱
  • 对图谱进行社区检测，形成主题簇
  • 为不同社区生成层次化摘要
  • 检索时结合图结构，支持局部和全局两种查询模式

它真正解决的是什么

  • 文档很多，但关键线索分散在不同段落、不同文件里
  • 问题不是“找一句原文”，而是“总结、归纳、串联、解释”
  • 需要知道谁和谁有关、哪些主题属于同一簇、整体脉络是什么

核心流程

索引阶段（Indexing）

  1. 文本切块
    将文档拆成多个 chunk，作为后续抽取和索引的基本单元。
  2. 实体抽取
    用 LLM 从每个 chunk 中抽取实体（节点）和关系（边）。
  3. 图构建
    合并重复实体，得到一张全局知识图谱。
  4. 社区检测
    用 Leiden 等算法对图进行聚类，形成不同主题社区。
  5. 摘要生成
    为每个社区生成摘要，作为后续全局检索的重要中间层。

为什么 GraphRAG 的建库成本更高

传统 RAG 一般只需要切块和 embedding。
GraphRAG 还要额外做实体抽取、关系抽取、图聚类、社区摘要，因此离线处理更重，但换来的是更强的结构化理解能力。

查询阶段（Query）

Local Search · 局部搜索

  • 适合针对具体实体的问题
  • 从相关实体出发，结合社区摘要和原始文本回答
  • 更像“围绕一个点向外扩展”

示例：

  • 某个人物参与了哪些项目？
  • 某家公司和哪些事件存在直接关系？

Global Search · 全局搜索

  • 适合需要全局视角的问题
  • 对所有社区摘要进行 map-reduce 式汇总后回答
  • 更像“先看全图，再做归纳”

示例：

  • 这批文档整体在讨论哪些主题？
  • 各主题之间的共识、分歧和演化方向是什么？

GraphRAG 更适合回答“总结型问题”，而不只是“定位型问题”

与传统 RAG 的对比

传统 RAG GraphRAG
检索方式 向量相似度 图结构 + 向量
跨文档推理 弱 强
全局问题 难以回答 Global Search 支持
构建成本 低 高（需要 LLM 抽取实体）
适用场景 事实性问答 复杂推理、报告生成

什么时候值得用 GraphRAG

适合

  • 企业知识库、研报、案例库、会议纪要这类多文档语料
  • 需要输出专题综述、结构化报告、跨文档分析
  • 对“关系”和“主题簇”敏感的任务

不太适合

  • 语料规模很小，普通 RAG 已经够用
  • 问题大多是简单事实问答
  • 对索引成本、处理时延、实现复杂度非常敏感

关键细节

1. 图谱质量决定上限

如果实体抽取不稳定、关系定义不清晰，后面的社区检测和摘要质量都会被拖低。
GraphRAG 的效果很大程度上取决于前面的结构化抽取质量。

2. 社区摘要是 Global Search 的关键

Global Search 不是直接在整张图上暴力搜索，而是依赖“社区级摘要”先压缩信息，再做汇总。
这一步决定了系统能不能给出高质量的全局回答。

3. 它不是传统 RAG 的完全替代

更现实的做法通常不是“只用 GraphRAG”，而是把它作为传统 RAG 的增强层：

  • 简单问题走向量检索
  • 复杂问题走图谱检索或全局摘要
  • 由路由策略决定调用哪一种检索方式

落地建议

如果你在做企业知识问答，可以先走一条更稳妥的路径：

  1. 先把普通 RAG 跑通
  2. 找出“回答不完整、跨文档关联弱、全局总结差”的问题
  3. 再为这部分高价值问题引入 GraphRAG

这样更容易评估它的真实收益，而不是一开始就把系统做得很重。

小结

GraphRAG 的价值不在于“检索更复杂”，而在于它让系统具备了更强的结构化理解能力。
当你的问题开始从“找到哪段文本”变成“这些内容之间是什么关系、整体说明了什么”，GraphRAG 往往就会比传统 RAG 更有优势。
